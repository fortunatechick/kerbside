Kerbside

A traffic analytics system that takes video from a fixed roadside camera and produces vehicle counts, per-vehicle speeds in km/h, lane assignment, size class and colour — using only classical digital image processing. No detector, no tracker-by-detection, no learned model anywhere in the pipeline.

What the project is

A counting and speed-measurement system, and the evidence that it works.

A camera is bolted to a pole and sees a road. From nothing but the pixels and a one-time geometric calibration, Kerbside recovers: how many vehicles passed, in which lane, in which direction, how fast, what size class, and what colour.

The hard constraint is that everything is done with classical digital image processing. That is not a handicap imposed for its own sake. It is what deployed traffic counting and speed measurement systems did for two decades before deep learning, and what many still do — because a pipeline of understood operators can be calibrated, audited and explained, and a network cannot.

Because this is a university project graded on how well it demonstrates those techniques, the interface is not decoration. It is the primary evidence. The operations console lets a user watch every operator run, change its parameters live, and see accuracy move in response.

Not an enforcement device

Kerbside measures speed. A legally admissible speed measurement device requires type approval and periodic calibration certification against traceable standards, and this project has neither. Vehicles above a configured limit are labelled “flagged for review”, never “violation”. No number plates or faces are read, stored or recognised, and nothing in the design would allow it.

The core premise

Why geometry is the whole game.

A camera measures pixels. A traffic engineer wants metres per second. Everything between those two sentences is one homography — the projective map between the road surface and the image plane — recovered once from four points a user clicks on the road.

Get that map right and the rest follows: a blob’s size in pixels becomes a footprint in metres, which becomes a vehicle class; its displacement between frames becomes a distance in metres, which divided by the frame interval becomes a speed. Get it wrong and every number the system produces is wrong by the same factor, consistently, with nothing in the output that looks incorrect. That is why the calibration view is one of the most carefully built parts of the project and why it insists on a two-point tape-measure check.

Technology stack

Chosen for reproducibility on a laptop with no GPU and no accounts.

Backend

  • Python 3.11+, installable with pip install -e .
  • NumPy — every operator is array arithmetic
  • OpenCV (headless) — decoding, and the fast paths for operators written out by hand elsewhere
  • SciPy — DCT, sparse graph traversal for connectivity, ndimage for component extents
  • FastAPI + Uvicorn — REST, MJPEG and WebSocket in one process
  • Pydantic v2 — request and response models
  • pytest, ruff, mypy --strict

Frontend

  • React 18 + TypeScript (strict: true, no any)
  • Vite, building to static assets served by FastAPI
  • Tailwind CSS v3 over a tokens.css of custom properties
  • Zustand for client state, TanStack Query for server state
  • Recharts for charts, lucide-react for icons
  • Radix UI primitives — accessibility plumbing only, no component library

Transport, and why it is split three ways

  • MJPEG over plain HTTP for the annotated video. A browser renders it natively in an <img>, with no decoder to ship and no buffering layer to go wrong.
  • WebSocket for per-frame telemetry — tracks, counts, speeds, stage timings. Small JSON messages at frame rate.
  • Ordinary REST for single-frame stage inspection, calibration and ablations. These are request/response by nature and gain nothing from a socket.

Raw frames are deliberately not pushed over the WebSocket. A 720p frame is 2.7 MB uncompressed; at 25 fps that saturates the socket and starves the telemetry the console actually needs to stay responsive.

Hard constraints

  • No machine learning anywhere in the pipeline. No neural networks, no YOLO, no Haar cascades, no HOG+SVM, no cv2.dnn, no pretrained weights. Classification is by real-world footprint from the homography, never by appearance.
  • Background modelling written by hand in NumPy. OpenCV’s MOG2 and KNN appear only as a clearly labelled reference baseline in the comparison study.
  • CPU only. Target ≥ 15 fps at 720p on a laptop.
  • Deterministic. Same video and parameters give byte-identical output. Every RNG is seeded.
  • Units in every identifier — speed_kmph, dist_m, dx_px, dt_s. Mixing pixels and metres silently is the single most likely source of a wrong answer here.

Three layers, one rule each

Operators

Pure functions of arrays and explicit parameters. No state, no globals, no I/O. Each is registered with an id, its syllabus unit, a parameter schema and a one-sentence rationale — which is what lets the inspector build a control for an operator it has never seen.

Stages

Named, parameterised steps that read a frame context, add to it, and report timing and metrics. Stateful ones (background model, tracker) implement reset(), which is called on any parameter change so a metric delta is never measured against stale state.

API

The only layer that opens a file, a socket or a camera. Every stage error carries a message a user can act on — a video that will not decode, a missing calibration, a parameter set producing zero detections — never a silent empty state or a stack trace.

The geometry

Written from the definitions, because everything downstream depends on it.

Recovering the homography

The user clicks four points bounding a rectangle on the road and types its real width and length. A normalised (Hartley) DLT, written out here rather than called, solves A h = 0 by SVD for the eight degrees of freedom. It recovers the rendering homography of a synthetic clip to within 1×10⁻⁹, and agrees with cv2.findHomography to under a thousandth of a pixel.

A four-point residual proves nothing

Four points determine a homography exactly, so its reprojection residual is zero by construction whatever the user clicked and whatever dimensions they typed. A calibration that is perfectly self-consistent can still be wrong by a constant factor, and every speed will be wrong with it. Two things catch that, and only two: the two-point distance tool checked against a tape measure, and the implied-camera plausibility check, which decomposes the matrix and reports the mounting height and tilt it implies so the user can compare against the pole they can see.

What the homography buys downstream

  • Perspective-scaled thresholds. The same car covers over a thousand times more pixels near the camera than at the horizon, so the expected footprint area is computed at each blob’s own road position rather than compared against one global threshold.
  • Perspective-scaled structuring elements. A half-metre morphological element is 37 px across in the near field and 3 px near the horizon. It is sized per image band from the geometry.
  • Off-plane reasoning. The focal length, the vertical vanishing point and the out-of-plane projection terms are all recoverable from the plane homography alone, so the pipeline can predict how far above its ground point a vehicle of a given height reaches — the difference between a footprint and a silhouette.
  • Elevated-plane homographies. The plane at height h differs from the road plane by one added term, which is what lets block-matching displacements be mapped through the plane the texture actually sits on rather than the road.

Data and ground truth

Built first, and built carefully, because every accuracy number is measured against it.

Hand annotation would be expensive, approximate, and — worst of all — unfalsifiable about geometry, which is the thing that matters most here. So the data comes from a renderer that projects cuboid vehicles through a known pinhole camera onto a road plane and records exactly what it did: world position, image bounding box, ground point, lane, speed, class, colour and occlusion, per vehicle, per frame.

What makes it a fair test rather than a rigged one

  • Cast shadows are physically constructed — each cuboid vertex projected along the sun direction onto the road, the hull darkened by a per-channel multiplication, so HSV value scales while hue and saturation survive. A small per-channel ambient correction models skylight, so the shadow-suppression tolerances are genuinely exercised rather than trivially satisfied.
  • Occlusion is measured, not assumed — silhouettes rasterised in painter’s order into an id buffer, and each vehicle’s visible pixel count compared against its unoccluded count.
  • Texture belongs to the vehicle, not the image — windows, lights, wheels and livery are geometry in the vehicle’s own frame, so block matching measures real texture displacement. Some bodies carry no livery at all, so the aperture problem is present in the data rather than hypothetical.
  • Stop-and-go emerges from car following, not from a scripted slowdown, so congested clips contain genuine queue formation and full stops.
  • The container frame rate can be made to lie on purpose, so the ingest stage’s timestamp measurement is a tested behaviour rather than a claim.

The nine stages

Each carries its syllabus units and a rationale, surfaced in the inspector.

S1
Ingest
Decode; record resolution, bit depth, codec. Measure the true frame interval from presentation timestamps rather than trusting the container, because every speed divides by it. Greyscale by ITU-R BT.601 with the weights exposed; HSV computed once for the stages that need it.

S2
Stabilise

Background
Running average (a temporal low-pass filter — the Unit 2 smoothing operator with time as its axis), temporal median, three-frame difference, and a fixed reference. Selective update freezes the model inside current foreground so a stopped vehicle is not absorbed. The difference is taken across colour channels, not luma.

Foreground
Otsu on the difference image, median filter for speckle, then perspective-scaled opening and closing, then hole filling. The closing element’s height is scaled by vehicle height rather than distance along the road.

S5
Shadow — the headline result
A foreground pixel is shadow when it is darker than the background but not black, no more saturated, and close in hue — measured circularly, and only where saturation is high enough for hue to be defined. Removing those pixels is what splits two vehicles a shadow had bridged into one blob.
Unit 7
S6
Blobs
Connected components at 4-, 8- or m-connectivity. A perspective-aware size filter, real-world shape plausibility, a watershed split for blobs too large to be one vehicle, and a geometric merge for fragments that fit inside one plausible silhouette. Lane assignment by point-in-polygon on the ground point.
Unit 1Unit 6
S7
Track
Greedy nearest-neighbour association gated in metres on the road plane, not pixels, centred on a constant-velocity prediction. Lifecycle: tentative → confirmed → coasting → terminated. Counting is a directed line crossing with a debounce. The distance metric is a parameter, so Unit 1’s three measures are compared for real.
Unit 1
S8
Speed — two independent routes
Route A differences the ground point’s road-plane position over a known interval. Route B tiles the vehicle’s box into blocks, gates them by texture variance, matches against the previous frame, takes the median vector, refines to sub-pixel by phase correlation, and maps it through the homography of the plane the texture sits on. Exhaustive, 2-D log and three-step searches all implemented and compared.

S9
Classify
Class by real-world footprint against documented length and width bands — written down as named constants so the rule can be inspected and disagreed with. Colour from an HSV histogram of body pixels with the darkest and brightest deciles discarded, and achromatic bodies named by value.

The operations console

A traffic operations console: dark, dense, quiet, legible from two metres.

Three regions, each scrolling independently. A left rail showing the pipeline as a vertical spine with per-stage timings and syllabus chips; the active view in the centre; an inspector on the right with the selected stage’s parameters and rationale. A collapsible bottom console logs every parameter change with its wall-clock cost and the resulting metric delta.

Views

  • Console — MJPEG stream with toggleable overlays, a motion-energy timeline with I/P frame colouring, live counts and a speed histogram.
  • Calibration — four-point clicking, a projected metre grid, the rectified bird’s-eye view, and the two-point distance validation tool.
  • Pipeline — stage thumbnails, a swipe-compare divider, and a pixel probe reporting RGB, HSV, background and difference values under the cursor.
  • Shadow Lab — four synchronised panels and a case list that jumps to frames where suppression changed the count.
  • Motion Lab — the motion vector field, and a clickable SAD search surface with all three search paths drawn on it.
  • Analytics — counts by lane and class, the 85th-percentile speed, headway distribution and the fundamental diagram.
  • Ablation Lab — nine presets, one click each.
  • Report — one button, a self-contained HTML and PDF.

Design rules that carry the look

  • Every number in monospace with tabular figures. This single rule is most of what makes it read as an instrument rather than a web page.
  • Colour tokens only — never a raw hex in a component. Dark ships first and ships flawless; light is a token swap.
  • Borders over shadows. One shadow, for overlays only.
  • Motion budget 120–180 ms, opacity and 2–4 px transforms only. No springs, no staggered lists, no page transitions.
  • The ground point is drawn as a filled dot at the bottom-centre of every box, because it is the point actually on the road and the thing every speed is computed from.
  • Focus ring on every interactive element; everything keyboard reachable.

Live recompute

Changing a parameter re-runs from that stage forward on the current frame. Debounced 120 ms while dragging, immediate on release, cached on a hash of frame id plus all upstream parameters, and run at preview resolution during a drag before reconciling at full resolution. Changed metrics flash with a ± badge for 1.5 s — green for improvement, red for regression. An apply to whole clip button re-runs the full video and updates aggregate accuracy, because single-frame feedback is for exploration and clip-level numbers are what get reported.

The limiting failure is fragmentation, not shadow: a vehicle whose dark window band survives thresholding arrives as two components, and counting them separately fails a count comparison exactly as a missed vehicle does. Shadow suppression itself removes 87–97% of true shadow pixels, scored against two renders identical but for cast_shadows — and rendering with no shadows at all barely moves frame agreement, which is how fragmentation was identified as the real constraint rather than assumed away.

Findings that changed the design

Each of these was found by measurement, and each would have produced plausible-looking wrong answers.

A greyscale background subtraction cannot see a red vehicle

BT.601 weights red at 0.299, so on this project’s own vehicle palette against its own asphalt, a red body differs from the road by 1.2 grey levels — and by 94 in its red channel. Blue, brown and green are within 10 levels too.

Body colourLuma differenceMax channel difference
red1.294.0
blue4.268.0
brown4.630.0
green9.134.0

Four of ten body colours were not merely hard to detect but invisible. The mask held their shadow and not them, which looks like a shadow problem and is a colour problem introduced two stages earlier. The difference is now taken across colour channels; the greyscale mode is kept as the baseline that demonstrates why.

Hue is undefined where saturation is near zero — and asphalt is neutral

At a background saturation of about 0.075, the hue difference across foreground pixels has a median of 10 and a 95th percentile of 67. That is not a measurement of colour; it is the arctangent of two small noisy differences. Applying the textbook 10-unit hue tolerance there rejects half of a correctly identified shadow, so the hue condition is enforced only above a saturation floor.

A closing element’s height must scale with vehicle height, not road distance

A silhouette extends upward from its ground point, and a metre of height projects at close to the across-road scale — about 25 px/m at image row 300 — while a metre along the road projects at about 4 px/m. Sized the wrong way the element comes out two pixels tall, the dark window band survives as a gap, and every vehicle is reported as a roof blob and a bumper blob. It presents as a tracking problem and is a structuring element that was six times too short.

The bounding-box ground point measures the vehicle’s near extremity

Not its centre — exactly half a vehicle length short, and exactly so for an unrolled camera, because the image row of a road point depends only on distance along the road. So absolute position carries a length / 2 bias. But that bias is constant for a given vehicle, so it cancels under differencing: an unbiased speed built on a biased position. The centroid, by contrast, has an error that grows with distance and with vehicle height (correlation 0.85), which never looks like a bug — it looks like trucks reading differently from cars.

Sub-pixel phase correlation needs more than a parabolic fit

For a fractional shift the inverse transform of a pure phase ramp is a periodic sinc whose side lobes alternate in sign, so fitting a parabola through the peak and its neighbours is fitting a parabola to something that is not remotely parabolic. It lands about a pixel out — and OpenCV’s phaseCorrelate has the same problem, measured. Refining on an upsampled DFT grid instead brings it under a tenth of a pixel.

m-connectivity and 8-connectivity always produce identical components

Provable, and asserted over random masks: if a shared 4-neighbour of a diagonal pair is foreground then a 4-path already joins them, and if neither is, m admits the diagonal directly. What m changes is the uniqueness of the path, which matters for boundary following and thinning, not for counting. The connectivity study therefore reports count differences between 4 and 8, and path ambiguity for m, rather than implying all three differ in the same way.

The twelve traps

Known in advance, handled by construction, and each one measured.

Limitations

Stated plainly, because a system that overstates itself is worse than one that underperforms.

  • Not an enforcement device. No type approval, no calibration certification, no evidentiary standing. Certified enforcement devices achieve far tighter tolerances than anything claimed here.
  • Accuracy depends entirely on a hand calibration. A self-consistent calibration can still be wrong by a constant factor, and every speed will be wrong with it. The two-point distance tool exists precisely to catch that, and a tape measure is the ground truth — not any table of nominal road dimensions.
  • The working range is finite. Beyond about 80 m a vehicle is a handful of pixels and a one-pixel error in its ground point is several metres of road. The system rejects blobs there rather than reporting measurements it cannot support, which is what a real counting camera does by being aimed at a working range.
  • Synthetic and real results are never conflated. Synthetic targets are hard gates because the ground truth is exact; real-footage figures are characterised honestly against a tape measure and a stopwatch, and reported separately.
  • Degradation is reported, not hidden. Counting and speed accuracy at reduced resolution and bitrate get worse. The study says by how much.
