The pipeline inspector

Each stage's real output for frame 95, with its timing, its metrics, and the one-sentence rationale the operator registry carries for it.

BackgroundU2U4 55.7 ms

Maintains a model of the empty road and subtracts it. The running average is literally a temporal low-pass filter - the Unit 2 smoothing operator with time as its axis - so a vehicle is whatever changes faster than its cutoff. The comparison is made in colour rather than luma, because a red vehicle has almost exactly the luminance of asphalt and is invisible to a greyscale difference. Selective update freezes the model inside foreground pixels so a stopped vehicle is not absorbed and does not leave a phantom behind when it moves off.

ShadowU7 47.7 ms

Classifies a foreground pixel as shadow when it is darker than the background but not black, no more saturated, and close to it in hue measured circularly. A shadow changes how the road is lit, not what it is made of, so hue and saturation survive while value drops. Removing those pixels is what splits two vehicles that a shadow had bridged into one blob - a miscount that looks like a tracking failure but was decided here.

BlobsU1U6 30.5 ms

Labels connected components and accepts each one only if its pixel area matches what a vehicle would cover at that place on the road, projected through the homography. A single global area threshold cannot work under perspective: set it to reject near-field noise and every distant vehicle disappears with it.

The class column is decided by the footprint in metres, not by appearance — a 3.6 m body is a car and a 6.0 m one is a light commercial. That is the substitution that removes the need for a trained detector.

Why this table has 3 rows and the console strip says 8

The strip reports the tracker's running count: every track that crossed a counting line, which is what the live telemetry carries. This table keeps only vehicles with a complete record — a lane, a direction, a footprint and a speed measured over enough frames to mean anything. The gap is tracks that were counted and then lost, or fragmented, before a full record existed. On a six-second clip that is most of them, and it is the Phase 3 fragmentation problem showing up in the analytics rather than being hidden by it.

This run is slow, and the reason is visible above

S8 dominates at 642 ms per frame, because block matching tiles every vehicle box and searches each block. The detection pipeline alone (S1–S6) runs at about 4 fps; with block matching enabled the whole thing drops to 1.1 fps. Both figures are below the 15 fps target, and both are reported rather than averaged into something more flattering.

Run it yourself

python run_kerbside.py --scenario free_flow --open renders the clip, starts the API and serves this interface on one port. No account, no API key, no GPU, no dataset download — the traffic is generated locally, with exact ground truth, from a seed.
