Kerbside

A traffic analytics system that watches a road through one fixed camera and measures every passing vehicle — using only classical image processing.

No machine learning anywhere in the pipeline

Open the live console → The real pipeline, running in your browser. No install needed.

What it does

From an ordinary video of a road, Kerbside reports four things about every vehicle:

🔢

Count

How many vehicles passed, per lane

⏱️

Speed

Each vehicle's speed in km/h

🛣️

Lane

Which lane it travelled in

🚗

Size & colour

Car, van, bus or two-wheeler, and its colour

The key idea

Most systems use a trained neural network to recognise vehicles by how they look. Kerbside recognises them by how big they are in real-world metres instead.

The user clicks four corners of a rectangle of known size on the road — for example, one lane wide and one road-marking long. From those four points the system computes a homography: an exact mapping between pixels in the image and metres on the road. After that, any position on the road can be measured in metres, so speed becomes distance divided by time, and a 4.5 m-long object is a car while an 11 m one is a bus. No training data is needed.

How it works

  1. CalibrateFour clicks on the road give the pixel-to-metre mapping.
  2. Learn the empty roadA background model built from the video itself shows what the road looks like with no traffic.
  3. Find what movedAnything that differs from the background is a candidate vehicle. Cast shadows are detected by colour and removed.
  4. Separate the vehiclesMorphology and connected components turn the pixels into individual vehicle shapes, sized for their distance from the camera.
  5. Follow themEach vehicle is tracked from frame to frame and counted when it crosses the counting line.
  6. MeasureSpeed is measured two independent ways and compared; size in metres gives the class, and the body colour is named.

Main features

  • Core techniques written by handBackground modelling, thresholding, shadow detection, the geometry, motion estimation and tracking are implemented from their definitions. A standard library handles video input and a few basic filters where speed matters.
  • Two ways to measure speedTracking the vehicle's position, and matching its texture between frames. Comparing them shows where errors come from.
  • Shadow removalShadows move with the vehicle and join neighbouring cars together; they are identified by colour and removed.
  • Built-in test trafficA traffic simulator renders roads with exactly known speeds, so every result can be checked against the truth.
  • Interactive web consoleLive video with overlays, adjustable settings for every step, and a view of each step's output.
  • Experiments and reportsNine comparison studies (e.g. which background method works best) and a one-click report.

Results

Every target was set before any code was written, and none has been changed afterwards. Five of the eight project milestones met their target; three did not.

The main finding: the shortfalls share one cause. The detection step sometimes splits a single vehicle into two pieces (for example, the roof and the bumper). This was proven by re-running the same scene with shadows switched off entirely — accuracy barely changed, so the problem is splitting, not shadows. The texture-matching speed method, which doesn't depend on the vehicle's outline, is twice as accurate as the position-based one, which confirms the diagnosis.

Limitations

  • Needs a fixed camera and a flat road — both are assumptions of the geometry.
  • Too slow for live video at present: about 1 frame per second at 720p. The online version runs in the browser at a smaller size (560×315) so a clip analyses in under a minute.
  • It measures speed but is not a speed-enforcement device, and never labels anything a violation. It does not read number plates or recognise faces.
