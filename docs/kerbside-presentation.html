Kerbside

Measuring traffic from one fixed camera, using nothing but classical image processing and geometry.

Vehicle counts, per-vehicle speed in km/h, lane assignment, size class and colour — from pixels and a one-time calibration. No neural network appears anywhere in the pipeline, and that is the point of the project rather than a limitation of it.

01The problem

A camera on a pole, and four questions

A traffic engineer with one fixed roadside camera wants to know how many vehicles passed, how fast each was going, which lane it used, and roughly what size it was. Every one of those is a measurement in metres and seconds, taken from an image indexed in pixels and frames.

What makes it hard

  • A pixel is not a metre, and how many metres it is worth changes with every image row.
  • Cast shadows move with the vehicle, so they are foreground by every motion test, and they bridge adjacent vehicles into one blob.
  • A dark window band splits one vehicle into a roof blob and a bumper blob.
  • The declared frame rate in a video container is frequently a lie, and speed divides by time.
  • Vehicles occlude one another, and the one behind is the one you lose.

The claim being tested

That a fully classical pipeline — background modelling, morphology, connected components, colour-space reasoning, block matching, and a planar homography — can produce a calibrated physical measurement, not just a detection.

A detector says vehicle. This system says 58.2 km/h, lane 2, 4.4 m long, and can show you which pixels and which geometry produced that number.

02Core premise

Geometry replaces the training set

A learned detector answers "is this a car?" from appearance. This project answers it from size in metres. That single substitution is what removes the need for any trained model.

Step 1

Calibrate once

Click four points on the road surface whose real-world rectangle you know — lane width across, dashed-line pitch along. That gives a homography: an exact map between the road plane and the image.

Step 2

Measure in metres

Any point on the road plane now has world coordinates. A blob's bottom-centre is on the road plane, so its position, and therefore its speed, is a physical quantity.

Step 3

Classify by footprint

Project the blob's ground extent to metres. 4.4 m long is a car; 11 m is a bus. No training data, no weights, and the decision boundary is a number a person can argue with.

The honest cost of this choice

Everything is now downstream of the mask. If segmentation splits a vehicle, the footprint halves and the class is wrong. A learned detector would be robust to that and would also be a black box that this module is not about. The trade is deliberate, and the measured consequences are reported on later slides rather than hidden.

05The geometry

Four clicks become a measuring instrument

The road is a plane. A pinhole camera maps a plane to a plane by a homography — a 3×3 matrix, 8 degrees of freedom, recoverable from four point correspondences. 

world (X across, Y along, Z=0 at road)
        │
        │  H  (3×3, computed by normalised DLT)
        ▼
image  (u, v) in pixels

Solved by hand, not cv2.findHomography:
  1. Hartley normalisation — centre each point
     set, scale so mean distance is √2
  2. Build the 2n×9 matrix A from the cross
     product constraint x × (H X) = 0
  3. h = right singular vector of A for the
     smallest singular value
  4. Denormalise:  H = T_img⁻¹ · Ĥ · T_world

The normalisation is not cosmetic. Without it the entries of A span pixel values squared against unity, the condition number explodes, and the fit degrades exactly where the perspective is strongest — the far end of the road, which is the part you most want to measure.

06Perspective scaling

The parameter that is a function, not a constant

Every size-valued parameter in the pipeline — minimum blob area, closing element, dilation radius, search window — is derived from the homography at the row where it is applied.

Two different scales at the same point

A metre across the road and a metre along the road project to wildly different pixel counts, because the road recedes and the across-direction does not. At image row 300 on the reference scene:

Across the road≈ 25 px/m
Along the road≈ 4 px/m
Vertical (height above road)≈ 25 px/m

The bug this caused

The morphological closing that bridges a vehicle's dark window band must be as tall as the vehicle, so it scales with the vertical rate — 25 px/m. It was originally sized on the along-road rate, 4 px/m, producing an element two pixels tall.

Result: the window band survived, and every vehicle was reported as a roof blob and a bumper blob. It presents as a tracking failure. It is a structuring element that was six times too short.

Elevated planes, for free

A vehicle roof is not on the road plane, so the road homography does not apply to it. But the homography for a plane at height h above the road follows directly: H_h = H + s·h·(K·r₃) in the third column. That is how the system draws a 3-D bounding box, and how it knows the roof pixel it is looking at is 1.5 m up rather than 8 m further away.

07Data and ground truth

Build the world, then measure it

You cannot report a speed error without knowing the true speed. Hand-labelled video gives you boxes, not velocities. So the project renders its own traffic with a synthetic renderer that knows every answer exactly.

What the renderer produces

  • Vehicles driven by the Intelligent Driver Model, so car-following and stop-and-go emerge rather than being scripted.
  • Correct occlusion via painter's-order draw with an ID buffer, so the ground truth records what is actually visible, not what exists.
  • Physically-constructed cast shadows: a per-channel multiplicative illuminant, not an additive grey tint.
  • Motion blur by shutter integration restricted to each vehicle's swept region.
  • Camera shake, rain, night lighting, low bit depth, compression.

The ground-truth contract

Per frame, per vehicle: world position, speed, lane, class, colour, the exact visible bounding box, and the visibility fraction.

Verified, not asserted: the renderer's own projection is checked against the calibration recovered from the rendered image to < 10⁻⁶ px against a 1 px gate. If those two disagreed, every error number in this project would be measuring the renderer.

Eight scenarios, each isolating one failure mode

free_flowcongested nightrain heavy_occlusioncamera_shake long_shadowsmotion_blur

Real footage is also supported and is used for qualitative checks. Synthetic and real results are never averaged together; a number is always labelled with the source that produced it.

S5 Shadow HSV test: value ratio in a band, low saturation change, small hue change. The hue condition is gated behind a saturation floor, because hue is undefined on neutral asphalt.
S6 Blobs Connected components, area gate by expected footprint at that row, watershed split, geometry-driven fragment merge. Both failure directions are handled: a watershed splits merged vehicles, a footprint test merges fragments of one.
S7 Track Constant-velocity prediction in world metres, greedy nearest-neighbour association, coast through occlusion. Gating in metres, not pixels — a 2 m gate is 2 m everywhere; a 40 px gate is 1.3 m near and 10 m far.
S8 Speed Two independent routes, computed for every vehicle and compared. The central experiment of the project. Next slide.
S9 Classify Footprint in metres → size band; dominant hue in the vehicle body region → colour name. Colour is sampled from the upper body, excluding the wheel and shadow rows, and only from pixels the mask claims.

Every stage carries a machine-readable rationale and its syllabus unit in the operator registry — 35 registered operators across units 1–8 — and the UI shows that text next to the parameter that controls it.

09The central experiment

Two ways to measure speed, deliberately disagreeing

Both routes are implemented in full and computed for every vehicle. The point is not to pick a winner in advance; it is to measure which one is better and be able to explain why. They are built to fail in independent ways, which is what makes the comparison informative.

Route A · ground point

Difference the ground point through the road homography

Take the bottom-centre of the bounding box — where the vehicle meets the road, and therefore the only point in the silhouette that genuinely lies on the calibrated plane. Convert two frames to world metres, divide distance by time.

Why it survives a known bias: that point is the vehicle's near extremity, half a length short of its centre. A real bias in position — but a constant one, so it cancels the instant two positions are differenced. An unbiased speed on a biased position.

Route B · block matching

Measure where the texture went

Tile the vehicle's box into blocks, discard the ones with too little texture to say anything, match the rest against the previous frame, take the median displacement, and refine it to sub-pixel by phase correlation.

The subtlety that decides whether it works: texture on a vehicle body sits about a metre above the road. Mapping its displacement through the road homography attributes it to the wrong plane, and the error scales with that height, so it never averages away. Using the homography of the plane at that height — one added term — removes the bias entirely.

The blob centroid is the naive third option, and it is rejected on geometry

The obvious thing is to track the centroid. But a centroid sits in the middle of the visible silhouette, which is not on the road plane, so the road homography does not apply to it at all. Its error grows with distance and with vehicle height — correlation 0.85 — which never looks like a bug. It looks like trucks genuinely reading differently from cars. The centroid is computed and used for association; it is never used for speed.

10The interface

An instrument, not a demo page

The UI exists so that a claim about the pipeline can be checked by looking, in one action. Every parameter is live; every stage output is inspectable.

Live console

Video with toggleable overlays — boxes, ground points, world trails, lane polygons, counting lines, mask, shadow, blobs. Counts and per-track numbers update per frame over the WebSocket.

Calibration

Click four points, get a reprojection RMSE, the implied camera height and tilt, and a plausibility verdict. A metre grid is drawn back onto the road so a wrong calibration is visible, not just a bad number.

Pipeline inspector

Every stage's intermediate image, its timing, its metrics, its rationale and its syllabus unit. Change a parameter, see which stages re-ran.

Shadow lab

The HSV test decomposed into its three conditions, each visualised separately, scored against a shadow-free render of the identical scene.

Motion lab

Block matching search strategies side by side: comparison count, PSNR of the predicted frame, and vector error against truth — the three numbers that show why cheap and accurate are different goals.

Ablation lab & report

Nine studies runnable from the browser, each with its question stated up front. One button emits a self-contained HTML report with every parameter embedded.

Design constraints that were enforced rather than aspired to: every number is monospace with tabular figures; every colour is a CSS custom property so light and dark are one token file; the parameter rail is generated from the backend's operator registry, so a new operator appears in the UI without a UI change.

The limiting failure is fragmentation, not shadow

A vehicle whose dark window band survives thresholding arrives as two components. Counting them separately fails a count comparison in exactly the same way a missed vehicle does. 144 split events against 38 merges.

A geometry-driven fragment merge in S6 — components that fit inside one plausible vehicle silhouette are joined — halved the splits to 87 and lifted recall to 0.83. The gate is still far off.

How that was proven rather than assumed

Shadow suppression itself is working: it removes 87–97% of true shadow pixels, scored against two renders identical but for cast_shadows.

The decisive experiment was an oracle: rendering the scene with no shadows at all barely moved frame agreement. If shadow were the constraint, removing it perfectly would have fixed the number. It did not. That is how fragmentation was identified as the real constraint instead of being guessed at.

Throughput was raised from 1.28 fps to 4.0 fps by profiling — scipy.ndimage.find_objects in place of a NumPy scatter costing 23 ms per call, flood-fill hole filling in place of iterated geodesic reconstruction, bounding-box component extraction, float32 through the mask stages, and downsampling in S2. It remains below target and is reported as such.

Why the mask-independent route wins — and why that is consistent

Route A's position is defined by the edge of the mask. Phase 3 established that this mask under-covers the vehicle rear and fragments. A short mask shortens the measured displacement, which under-reads the speed — the −14.35 km/h bias is exactly that, measured. Route B never touches the mask boundary; it matches texture inside the box. Two methods built to fail differently point at the same defect, which is the strongest evidence in the project that segmentation, not measurement, is the binding constraint.

Route B's residual is structural, not a tuning problem

A parameter sweep over the smoothing window and gain moved Route B's MAE between 9.4 and 9.6 km/h — essentially flat. The remaining −3.9 km/h is not reachable from S8; it has to be fixed at S4–S6, where the mask is made. The flat sweep is the result. Tuning until a number looked better would have hidden it.

15Finding

A greyscale background subtraction cannot see a red vehicle

BT.601 weights red at 0.299. On this project's own vehicle palette against its own asphalt, a red body differs from the road by 1.2 grey levels — and by 94 in its red channel.

Four of ten body colours were not merely hard to detect but invisible. The mask held their shadow and not them, which presents as a shadow problem and is a colour problem introduced two stages earlier.

The difference is now taken across colour channels (difference_mode = max_channel). The greyscale mode is kept in the codebase as the baseline that demonstrates why.

16Findings

Two textbook methods that fail on their stated assumptions

Hue is undefined where saturation is near zero — and asphalt is neutral

At a background saturation of about 0.075, the hue difference across foreground pixels has a median of 10 and a 95th percentile of 67. That is not a measurement of colour; it is the arctangent of two small noisy differences.

Applying the textbook 10-unit hue tolerance there rejects half of a correctly identified shadow. The hue condition is now enforced only above a saturation floor.

Sub-pixel phase correlation needs more than a parabolic fit

For a fractional shift, the inverse transform of a pure phase ramp is a periodic sinc whose side lobes alternate in sign. Fitting a parabola through the peak and its two neighbours is fitting a parabola to something that is not remotely parabolic.

It lands about a pixel out — and OpenCV's phaseCorrelate has the same problem, measured. Refining on an upsampled DFT grid brings it under a tenth of a pixel.

m-connectivity and 8-connectivity always give identical components

Provable, and asserted over random masks. What m-connectivity changes is the uniqueness of the path, which matters for boundary following — not the set of components, which is what most write-ups imply.

A block matcher's sign convention is not a detail

A codec's motion vector is the negation of the content displacement. Reported the codec way, it would have silently disagreed with phase correlation on every frame. The API now returns content displacement and offers the codec form explicitly.

19Limitations and ethics

What this system is not

Not a speed enforcement device

The system measures speed. It never asserts legal accuracy, never issues a violation, and has no evidentiary standing. Over-limit rows are labelled "flagged for review" everywhere they appear — in the UI, the API and the generated report.

A legally admissible speed device requires type approval and calibration certification that this project does not have and does not claim.

No personal data, by construction

Number plates and faces are never read, stored, or recognised. The only privacy feature in the codebase is blurring; there is no recognition capability to disable, because none was written.

Known technical limits

  • 4.0 fps at 720p, against a 15 fps target.
  • 25% frame count agreement, against a 98% gate.
  • Class accuracy 52%, because footprint is downstream of a mask that fragments.
  • Requires a fixed camera and a flat road; both are assumptions of the homography, not of the code.
  • Calibration quality bounds everything. A 2% distance error is a 2% speed error, permanently.

What I would do next

  • Attack fragmentation at S4 with a colour-consistency region grow seeded from the mask, rather than patching at S6.
  • Vectorise the per-row morphology into banded strips to close the throughput gap.
  • Extend the ground-truth comparison to the occlusion and night scenarios, which are currently qualitative only.
20In summary

What this project demonstrates

Geometry can do a detector's job

A calibrated homography turns classification into arithmetic on metres, and turns a tracked blob into a physical speed. No training data appears anywhere.

Two independent routes agreed on the root cause

The mask-dependent route under-reads by 14 km/h; the mask-independent one by 4. Two methods built to fail differently pointing at the same defect is what turns a number into a diagnosis.

Textbook methods were tested, not assumed

Greyscale differencing, the hue tolerance, the parabolic sub-pixel fit and the fixed structuring element each failed on their own stated assumptions, and each failure is documented with the measurement that caught it.

A missed target is reported as a missed target

Phase 3's gate was not met. The diagnostic work that followed — the shadow-free oracle experiment — is more informative than a met gate would have been.

Every number on these slides is produced by a test or a script in the repository and can be regenerated from the source video and the recorded parameter set. The console can reproduce any of them interactively, and the report button emits a self-contained HTML file with the full parameter state embedded.
